3JavaScript cheat sheet for GDevelop

These calls were checked against GDevelop's own runtime code. If your AI uses a function that is not in this list, check it before you trust it.

// runtimeScene : the scene the event is in
// objects      : the instances your conditions picked (the event takes ONE object parameter)

runtimeScene.getObjects("Enemy")                    // EVERY Enemy in the scene
obj.getX()  obj.getY()  obj.setX(n)  obj.setY(n)    // position
obj.deleteFromScene()                               // remove it (no argument)
runtimeScene.createObject("Enemy")                  // make a new one, returns it
// getObjects("Player")[0] is undefined when there is no Player, so check it first: if (player) { ... }

runtimeScene.getVariables().get("Score").add(1)     // scene variable
obj.getVariables().get("hp").sub(10)                // object variable
variable.setNumber(n)   variable.getAsNumber()   variable.getAsString()

runtimeScene.getTimeManager().getElapsedTime()      // time since last frame, in MILLISECONDS
console.log("hello")                                // prints to the browser console

Three rules that catch most bugs

  1. Milliseconds. getElapsedTime() returns milliseconds. Divide by 1000 to get seconds.
  2. objects or getObjects(). objects holds only the instances your conditions picked. getObjects() returns every instance in the scene. Using getObjects() where you meant objects damages every enemy at once.
  3. One object parameter. A JavaScript event takes a single object. Put the condition that picks it (for example Player collides with Coin) above the code event.
  4. deleteFromScene() takes no argument. Older examples online write deleteFromScene(runtimeScene). It still works, but you do not need the argument.

Sample block to practise on

No project open, or no code yet? Paste this into your AI. Object parameter: Coin. A condition above it, Player collides with Coin, picks the coins.

for (const coin of objects) {
  runtimeScene.getVariables().get("Score").add(
    coin.getVariables().get("value").getAsNumber()
  );
  coin.deleteFromScene();
}

Ask for a tester bot

I'm making a [genre] game in GDevelop 5. Controls: [arrow keys to move, space to jump].
I want a small tester bot as a JavaScript code event, in an event group I can switch off, that:
- presses a random key, holds it for a random 100 to 500 ms, then releases it, like a monkey. The event runs every frame, so keep the timer and the held key in scene variables, not in let variables
- sets the time scale once at the start of the scene, not every frame
- writes to the console when the player is stuck for 20 seconds, falls out of the level, or dies, with the position
- can be switched off with one variable

Calls you may use for input and time:
runtimeScene.getGame().getInputManager().onKeyPressed(keyCode, 0) and onKeyReleased(keyCode, 0)
runtimeScene.getTimeManager().setTimeScale(n)
runtimeScene.getTimeManager().getElapsedTime()

First give me a plan and your assumptions. Then the code. Then tell me what I should read in the console.

5Five checks before you keep code

  1. Does it run? Preview with the debugger and open its console. No red errors.
  2. Does it do what you asked? Watch it in the game, not just in the code.
  3. Do the calls exist? Compare against the cheat sheet.
  4. Does it hold up? Try zero enemies, a hundred enemies, pause and restart. Watch for values that reset every frame.
  5. Can you explain it? Ask your AI to explain it line by line, then keep it in a named, commented group in your event sheet.

6Maps and UI: ideas to try

Maps

  • Ask the AI for a grid of text, for example 30 wide and 12 tall, with a letter for each tile. Pegs and slots for a Plinko board work the same way.
  • AIs miscount grids. Ask it for a short function that checks the exit is reachable.
  • Your code reads each letter and creates the matching object at the right position. That is a good use of JavaScript.
  • Check it in the game: can you get from start to exit, is it too empty or too crowded, does it feel fair.

UI

  • Ask for the screens first: title, pause, game over, settings, and what goes on each.
  • Then ask for positions relative to the screen size, with a safe margin.
  • Then text size, contrast, and a short message when something changes.
  • Check it on a small screen, and hand it to someone and watch their first 30 seconds.

7Tester bots: ideas to try

A tester bot is a small program whose only job is to play your game and report what breaks. Keep it in an event group you can switch off, and remove it before you ship.

BotWhat it doesWhat it finds
MonkeyPresses random keys at random timesCrashes, falling out of the world, getting stuck
Human-likeReacts slowly, makes mistakes, holds keys for different lengthsWhether the difficulty feels fair for a person
Goal-seekerFollows simple rules: head for the exit, jump at gapsWhether a level can be finished at all
Monte CarloRuns the numbers (waves, upgrades, odds) many times with random choices and counts the resultsWin rate, run length, which upgrade is always picked

What a bot can do in GDevelop

  • Press and release keys, and use the mouse, from a JavaScript code event.
  • Speed up time a little with the time scale, 2x or 3x. Very high speed can break physics, which matters for a Plinko ball, so start low.
  • A sped-up game still runs in real time, so hundreds of runs of a whole game take hours. For Monte Carlo, simulate just the numbers in plain JavaScript.
  • Write what happened to the console: where the player got stuck, fell out, or died.
  • Not tell you the game is fun. A person has to play it for that.

Which bot fits which game

GameGood botLook for
PlatformerMonkey, then goal-seekerFalling out of the world, a gap that cannot be jumped, getting stuck
Co-op horrorMonkey. In Roblox, a test script that moves a characterDoors or puzzles that can be skipped, getting stuck in a room
Tower defenseMonte Carlo on the wave numbersA tower or wave that is far too strong or too weak
Plinko DungeonMonte Carlo on the numbersHow often the boss dies, which upgrade is chosen every time

A tiny monkey bot, as an idea

An idea sketch. It checks out against GDevelop's runtime code, but it has not been tried in a full game yet, so test it in a preview before relying on it.

// Runs every frame, so the bot's state lives in scene variables.
const v = runtimeScene.getVariables();
const input = runtimeScene.getGame().getInputManager();
const keys = [37, 38, 39, 40, 32];      // arrows and space

if (v.get("BotT").getAsNumber() <= 0) {
  const k = keys[Math.floor(Math.random() * keys.length)];
  input.onKeyPressed(k, 0);               // press a random key
  v.get("BotKey").setNumber(k);
  v.get("BotT").setNumber(100 + Math.random() * 400);   // hold for ms
} else {
  v.get("BotT").sub(runtimeScene.getTimeManager().getElapsedTime());
  if (v.get("BotT").getAsNumber() <= 0)
    input.onKeyReleased(v.get("BotKey").getAsNumber(), 0);
}
// Speed-up: setTimeScale(2) ONCE at the start of the scene.

8AI skills: rules your AI loads every time

A skill is a short text file of rules, called SKILL.md, that your coding AI loads for you, so you do not retype the same rules in every prompt. In a chat AI with no skills, paste the same text at the start of the chat. A good one removes a habit you keep correcting. A bad one adds noise, so read it before you install it.

Three worth knowing

SkillWhat it doesFor this class
ponytailMakes the AI write only what the task needs. It checks, in order: does this need to exist, is it already in the project, does a built-in feature cover it. It never cuts validation or error handling. /ponytail-review reviews a diff.Matches our rule: use a built-in event or action before you write JavaScript. The author's benchmark claims about half the code. An independent test found a smaller gain, so treat the number as a claim.
unslopFifteen lines. It checks your git diff and removes what a human would not have written: comments that repeat the code, extra defensive checks, casts to get around type errors, tests that test nothing, style that does not match the file.Made for code files in git. A GDevelop event sheet is saved inside the project file, so the diff is hard to read. Paste one block into your AI with the same list instead. Several skills share the name, so check the author.
awesome-gamedev-agent-skillsA bundle of 77 game-dev skills, Apache-2.0, for Godot, Unity, Unreal, Phaser, PixiJS, three.js, Bevy, pygame, LÖVE, Defold and Roblox. A router loads the one that matches your engine.GDevelop is not in it. The Phaser and PixiJS skills are the nearest for JavaScript, and the Roblox team can try the Roblox one. Install only the router plus one engine: claude plugin marketplace add gamedev-skills/awesome-gamedev-agent-skills, then claude plugin install router@awesome-gamedev-agent-skills. Kenan has not tried these in class.

Before you install any skill: read its SKILL.md, install it only from the author's own repository, and remember it runs with your AI's permissions. Some also install hooks that run on your computer. None of these knows GDevelop, which is why the next one exists.

A JavaScript and game check made for this class

Written for GDevelop 5 JavaScript events. It has not been tested across AIs, so if it helps or fails, tell Kenan. In Claude Code, save it as .claude/skills/gdevelop-js-check/SKILL.md in your project folder. Anywhere else, paste it at the start of the chat. Roblox team: swap the GDevelop rules for the Luau ones in section 10.

---
name: gdevelop-js-check
description: Write or review JavaScript code events for a GDevelop 5 game. Use when asked to write, fix or review GDevelop JavaScript.
---
You are helping with a GDevelop 5 game. Be short and plain.

Before writing code
1. If a normal event or a built-in action does it, say so and stop. Events are for wiring. JavaScript is for loops, maths and rules reused with different numbers.
2. List your assumptions: object names, variable names, and what the conditions above the event pick.

Rules for the code
- The event takes ONE object parameter. objects holds only the instances the conditions picked. getObjects("Name") returns every instance in the scene. Do not use getObjects where a condition should pick.
- getObjects("Name")[0] can be undefined. Check it before you use it.
- The event runs every frame, so a let or const starts fresh every frame. Keep state in scene or object variables.
- getElapsedTime() is in milliseconds. Do not use setTimeout or setInterval: they ignore pause and the time scale. Use a timer variable.
- Do not create objects, build arrays or call console.log every frame unless that is the point.
- Use only the calls I list. If you are not sure a call exists, say so.
- Names are case sensitive and must match my objects and variables.
- Change the GDevelop object, not its renderer (Pixi) object. The engine overwrites the renderer object every frame.

Remove slop
- Comments that repeat the code.
- try/catch or null checks around things that cannot fail.
- A helper used once, unused variables, options nobody asked for.
- Logging or tests that check nothing.

After the code
- Say what to test in a preview: zero objects, many objects, pause, restart.
- Say what you did not check.

Two of these rules, objects against getObjects and the renderer object, come from GDevelop's own page on JavaScript events, which is worth reading once.

9Watch out for these in your prompts

Watch outWhat goes wrongDo this
No engine namedYou get Unity, Phaser or plain browser code.Say GDevelop 5, a JavaScript code event. Roblox teams say Roblox Studio and Luau.
A vague goalThe AI invents the design: "make enemy AI".Say it in game terms with numbers: spawn one enemy every 3 seconds, at most 10 at once.
Pasting the whole projectThe AI loses the point and changes things you did not ask about.Paste one block, its object parameter, and the names it uses.
"It doesn't work" with no errorThe AI guesses.Paste the console message, the code, and what you expected to happen.
Invented callsThe code looks right and does nothing, or errors.Give it the list of calls and ask it to flag any it is unsure of.
Asking for everything at onceA 200-line block nobody can read or fix.One job per block. Plan first, then code.
"Be careful" and "be robust"You get try/catch and checks everywhere, which hide real errors.Say what can really fail, and guard only that.
Believing "this should work"An AI sounds as sure when it is wrong.Run the five checks. Running it is the proof.
Pasting private thingsKeys, passwords and other people's details end up in a prompt.Leave them out. Use a made-up value.
Text from a web page or forumPasted text can carry instructions, and a coding AI may follow them.Paste only what you read and trust. Read what the AI did before you accept it.
Losing the promptYou cannot explain the code, or show where it came from.Keep the prompts that worked. AI-written code goes in CREDITS.md, and you must be able to explain it.
